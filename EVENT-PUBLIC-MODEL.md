# Event Public Model

## Intention

La fiche publique d'un evenement est la page que le visiteur consulte pour
comprendre rapidement ce qui est propose, decider si l'evenement l'interesse et
savoir quoi faire ensuite.

Elle ne doit pas ressembler a une fiche d'administration. Elle doit etre claire,
lisible et orientee visiteur.

La question centrale est :

> De quoi s'agit-il, quand cela a-t-il lieu, ou cela se passe-t-il, et comment
> obtenir les informations utiles ?

## Principe general

La fiche publique doit presenter l'evenement comme une reference partageable.

Elle doit :

- donner envie de lire ;
- rendre les informations essentielles immediatement visibles ;
- rester utile meme si certains champs optionnels ne sont pas renseignes ;
- ne jamais afficher de zones vides ;
- ne pas exposer de vocabulaire technique ;
- rester simple avant d'ajouter des fonctions avancees.

L'evenement reste la source de verite. Le flyer, les images et les liens
accompagnent la communication, mais ne remplacent pas les informations saisies.

## Ordre recommande V1

### 1. Etat particulier

Si l'evenement est annule, l'information doit apparaitre avant tout le reste.

Le visiteur doit comprendre immediatement que l'evenement ne se tiendra pas, sans
avoir a lire toute la page.

Affichage attendu :

- mention claire : Annule ;
- phrase courte si une precision est disponible plus tard.

N'apparait pas si l'evenement n'est pas annule.

### 2. Illustration principale / Flyer

L'image doit ouvrir la fiche lorsque l'evenement possede un visuel.

Elle peut provenir :

- de l'image principale ;
- d'une illustration ajoutee a l'evenement ;
- d'un flyer image ;
- d'une image par defaut future si rien n'est fourni.

L'objectif est de rendre l'evenement reconnaissable et partageable.

Le flyer PDF ne remplace pas l'image principale. Il peut etre propose plus bas
comme document a consulter ou telecharger.

### 3. Titre

Le titre est l'information principale.

Il doit etre visible sans effort et ne pas etre masque par les actions ou les
informations secondaires.

Le titre est obligatoire pour une fiche publique exploitable.

### 4. Type(s) d'evenement

Les types aident le visiteur a situer l'evenement.

Exemples :

- Atelier ;
- Stage ;
- Rencontre ;
- Non classe si aucun type plus precis n'a ete choisi.

Les types doivent rester discrets. Ils orientent, mais ne doivent jamais prendre
la place du titre ou des dates.

### 5. Date(s)

Les dates doivent etre visibles tres tot dans la page.

Pour chaque date, afficher :

- le jour ;
- la date ;
- l'heure de debut si elle existe ;
- l'heure de fin si elle existe ;
- la mention Toute la journee si applicable ;
- la mention Annulee si seule cette date est annulee.

Les dates doivent etre presentees dans l'ordre chronologique.

Si l'evenement contient plusieurs dates, le visiteur doit comprendre qu'il s'agit
du meme evenement propose a plusieurs moments, et non de plusieurs evenements
separes.

### 6. Lieu

Le lieu indique ou se deroule l'evenement.

Afficher si disponible :

- nom du lieu ;
- adresse ;
- lien du lieu si renseigne ;
- informations complementaires propres a l'evenement.

Les informations complementaires doivent rester separees du lieu lui-meme.

Exemples :

- Entree par la cour ;
- Salle communiquee prochainement ;
- Merci de ne pas stationner dans l'impasse.

Si aucun lieu n'est defini, ne pas afficher de section vide.

### 7. Personnes avec roles

Les personnes aident le visiteur a identifier qui organise, intervient ou repond
aux questions.

Afficher pour chaque personne :

- nom ;
- role(s) pour cet evenement ;
- telephone si renseigne ;
- email si renseigne ;
- lien si renseigne.

Les roles appartiennent a l'evenement. Ils doivent donc etre affiches ici, meme
si la personne est reutilisee ailleurs.

Exemples de roles :

- Organisateur ;
- Intervenant ;
- Contact inscription ;
- Contact information.

Si aucune personne n'est renseignee, ne pas afficher de section vide.

### 8. Description

La description donne le contexte, le sens et les details utiles.

Elle peut expliquer :

- ce que le visiteur va vivre ;
- a qui s'adresse l'evenement ;
- pourquoi participer ;
- les informations pratiques non couvertes par les autres sections.

La description est recommandee, mais elle ne doit pas devenir obligatoire pour
tous les cas. Certains evenements peuvent etre principalement portes par un
flyer ou une illustration.

### 9. Illustrations et flyer

Apres les informations essentielles, la fiche peut afficher les supports de
communication associes.

Afficher selon les elements disponibles :

- illustrations supplementaires ;
- flyer image ;
- flyer PDF.

Le flyer PDF doit etre presente comme un document utile, pas comme la source
principale des informations.

Si aucune illustration supplementaire ni flyer n'existe, cette section disparait.

### 10. Actions utiles

En V1, les actions publiques doivent rester limitees.

Actions possibles a terme :

- Ajouter a mon calendrier ;
- copier le lien ;
- partager ;
- telecharger le flyer PDF ;
- afficher ou telecharger le QR Code.

Pour la premiere fiche publique, ces actions peuvent etre preparees dans le
modele, mais elles ne doivent pas toutes etre developpees immediatement.

### 11. Evenements lies

Les evenements lies ne font pas partie de la premiere version.

Ils pourront etre utiles plus tard pour proposer :

- d'autres dates similaires ;
- d'autres evenements du meme type ;
- d'autres evenements au meme lieu ;
- d'autres evenements avec la meme personne.

Cette zone ne doit pas etre ajoutee tant que le besoin public n'est pas valide.

## Informations obligatoires

Pour qu'une fiche publique soit utile, elle doit au minimum disposer de :

- un titre ;
- au moins une date.

Ces deux informations permettent de comprendre ce qui est annonce et quand cela
se passe.

## Informations fortement recommandees

Les informations suivantes ameliorent fortement la qualite de la fiche publique,
mais ne doivent pas bloquer tous les cas :

- illustration principale ou flyer image ;
- description ;
- lieu si l'evenement se deroule dans un lieu physique ;
- au moins un contact si une inscription ou une question est attendue ;
- type d'evenement.

## Informations optionnelles

Les informations suivantes apparaissent uniquement si elles existent :

- plusieurs dates ;
- horaires ;
- mention toute la journee ;
- lieu ;
- adresse ;
- lien du lieu ;
- informations complementaires du lieu ;
- personnes ;
- roles multiples ;
- telephone ;
- email ;
- lien d'une personne ;
- illustrations supplementaires ;
- flyer PDF.

Aucune section vide ne doit etre affichee au visiteur.

## Ce qui n'apparait pas encore

La premiere fiche publique ne doit pas encore afficher :

- formulaire de reservation ;
- paiement ;
- billetterie ;
- nombre de places disponibles ;
- liste d'attente ;
- carte Google Maps ;
- coordonnees GPS ;
- commentaires publics ;
- statistiques ;
- contenu provenant obligatoirement de WP Seed Content ;
- blocs de mise en page avances ;
- constructeur de page interne.

## Futures phases

### Ajouter a mon calendrier

Le bouton Ajouter a mon calendrier sera ajoute dans une phase dediee.

Le visiteur ne doit pas voir le terme technique ICS comme action principale.

### QR Code

Le QR Code sera utile pour les flyers, affiches et supports imprimes.

Il doit pointer vers la fiche publique de l'evenement.

### Cartographie

Une carte pourra etre etudiee plus tard, mais elle ne fait pas partie de la
premiere fiche publique.

Si elle arrive un jour, elle devra rester optionnelle et ne pas rendre Google
Maps obligatoire.

### Reservation et inscription

La reservation, l'inscription avancee, le paiement et la billetterie sont hors
perimetre de la premiere fiche publique.

Une action simple de contact peut suffire tant que le besoin metier n'est pas
valide.

### Evenements lies

Les evenements lies pourront enrichir la navigation lorsque plusieurs fiches
publiques existeront.

Ils doivent rester secondaires et ne jamais distraire du contenu principal.

## Regles d'affichage

- L'information importante passe avant les actions.
- Le visiteur doit comprendre l'evenement sans ouvrir un flyer PDF.
- Une section vide n'apparait jamais.
- Les dates sont toujours ordonnees chronologiquement.
- Une date annulee reste visible avec une mention claire.
- Un evenement annule reste consultable, mais l'annulation domine la page.
- Les informations techniques ne sont pas exposees au visiteur.
- Les medias soutiennent la comprehension, sans remplacer les donnees de l'evenement.
- Les actions futures doivent rester discretes tant qu'elles ne sont pas utiles.

## Resume

La premiere fiche publique de WP Seed Events doit presenter un evenement dans un
ordre simple :

1. etat particulier si annule ;
2. illustration principale ou flyer ;
3. titre ;
4. type(s) ;
5. date(s) ;
6. lieu ;
7. personnes et roles ;
8. description ;
9. illustrations et flyer ;
10. actions utiles plus tard ;
11. evenements lies plus tard.

La V1 doit privilegier une fiche claire, partageable et lisible, sans reserver,
sans payer, sans carte obligatoire et sans builder.
